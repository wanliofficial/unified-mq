# S0.2 Spike Report: Raft 分组模型

**结论：每分区一个 Raft Group 的资源开销随组数线性增长（约 3 进程 / 2 ETS / 128KB / 5ms 启动 每组），但并不提升单写入者吞吐。分组策略应受"单节点可承载组数预算"与"故障域"共同约束，而非按分区数 1:1 建组。建议默认每组 16 个分区，并允许按租户下探到 1。**

- **对应 Roadmap**：`docs/roadmap.md` §2 S0.2、§6.2（消息复制层按 S0.2 结论决定分组模型）
- **决策落点**：ADR-008（分区 Raft 分组模型 + 故障域定义）
- **版本 / 环境**：`rabbitmq/ra` 3.2.0（同 S0.1，ref `2d81d2`），OTP 28.3.1，单节点单 BEAM
- **代码**：`spikes/s0_2_grouping/`；运行 `./run_cluster.sh` 即 `./run_s0_2.sh`

## 1. 实验设计

本 spike 是 **单节点** 实验：在单个 BEAM 上建 K 个互相独立的 1-voter ra 组（组名 `g1..gK`），每个组跑同一个最小计数器状态机（`s0_2_machine`）。对每个 K 测量：

1. **组形成开销**：`start_or_restart_cluster/5` 逐一拉起 K 组的耗时；
2. **资源占用**：ra 启动后、建组前取基线，建组后取进程数 / ETS 表数 / 内存，求每组增量；
3. **写入吞吐与尾延迟**：向 K 组轮询发 `?W=2000` 条写，记录每条墙钟耗时，得聚合吞吐与 p50/p95/p99。

K 取值：`[1, 4, 8, 16, 32, 64, 128]`。

**为什么单节点就够**：本问的核心是"拥有 N 个 Raft 组"的**机器开销**（进程、ETS、WAL、选举定时器），与网络/复制成本无关。每组的**复制写成本**已由 S0.1 钉死（3 节点 ~677 µs/写）。两者相乘即得生产估算，无需在单节点 spike 里再拉 3 节点 × 128 组。

**已知局限（必须诚实记录）**：
- 写入驱动是**单进程串行**分发，因此聚合吞吐被"单写者 + 本地一次 fsync"的地板锁死，不能反映真实多生产者 / 多 leader 并行时的聚合吞吐；
- CPU 未做按组隔离观测（组进程本身轻量，主要成本在 WAL/fsync）；
- 单节点下所有组共享一块磁盘与一次 fsync 路径，故吞吐不随 K 上升——这是单节点 artifact，不是结论。

### 2.1 每组固定开销（线性）

以基线（89 进程 / 35 ETS / 45MB）为基准，各组增量高度恒定：

| 指标 | 每组增量 | 说明 |
|---|---|---|
| 进程数 | **+3 / 组** | `ra_server_proc` + `ra_log` + WAL 相关 worker |
| ETS 表 | **+2 / 组** | 日志元数据 + 快照状态表 |
| 内存 | **~110–256 KB / 组** | 随组数增大而摊薄（固定开销占比下降），128 组时约 109 KB/组 |
| 启动耗时 | **~4–6 ms / 组**（warm） | K=1 的 108ms 是冷启动（首个组触发 ra 默认系统首次 WAL 初始化），不具可比性；warm 趋势线性 |

> 线性验证：64→128 组，进程 +192（恰 3×64）、ETS +128（恰 2×64），完美线性。

### 2.2 吞吐与尾延迟（不随 K 变化）

| K | 聚合 writes/s | p50 | p99 |
|---|---|---|---|
| 1 | 1089 | 866 µs | 1563 µs |
| 128 | 1063 | 889 µs | 1559 µs |

吞吐在 **~1070 writes/s 几乎不变**，p50 ≈ **866 µs ≈ S0.3 的 fsync 地板（871 µs/msg）**。这是因为本实验是单进程串行派发，每条写都落一次本地 fsync；组再多也只是多了几把并行的锁，单写者依旧被串行地板卡住。

**这一点不否定分组的价值**，而是说明：在本单机单写者设定下，吞吐由"每条消息一次共识/fsync"决定（印证 README 6.2"本地数据面走批量追加，不将每个业务操作变为全局共识命令"）。真实生产中组间并行来自**并发生产者 + 分布在不同节点上的 leader**，其每组的复制写成本直接取 S0.1 的 677 µs。

## 3. 分组策略与故障域（ADR-008 输入）

设某节点承载 P 个分区，每组 G 个分区，则组数 `N = ceil(P / G)`：

```
进程 ≈ 89 + 3N       ETS ≈ 35 + 2N       内存 ≈ 45MB + 0.125MB·N
启动 ≈ 5ms·N        故障域 = G 个分区（一次该组 leader 选举/故障会短暂暂停这 G 个分区的复制）
```

取 G = 16 的预算示例：

| 节点分区数 P | 组数 N | 进程增量 | ETS 增量 | 内存增量 | 启动 |
|---|---|---|---|---|---|
| 128 | 8 | +24 | +16 | ~1 MB | ~40 ms |
| 1024 | 64 | +192 | +128 | ~8 MB | ~320 ms |
| 4096 | 256 | +768 | +512 | ~32 MB | ~1.3 s |

### 推荐

1. **默认 `G = 16`（每组 16 分区）**，并把"单节点组数 N"作为资源预算硬上限来反推 G：
   - 推荐 N ≤ ~256/节点（≈ +768 进程、+512 ETS、+32MB、启动 ~1.3s，皆宽松）；
   - 超过该预算时**增大 G**（如 32/64），而不是增加组数。
2. **故障域 = G 分区**：一次组的 leader 选举或局部故障只会短暂暂停这 G 个分区的复制（README 5.3 警告的正是对"故障波及面"的约束）。G 越小隔离越好、开销越大；G 越大开销越小、爆炸半径越大。G=16 是隔离与开销的折中默认。
3. **允许按租户/命名空间下探到 `G = 1`**：强隔离需求（单租户热点分区不应连累其他租户的重选举）或少分区场景，可一分区一组。
4. **不要 1:1 全量建组**：对 4096 分区若 G=1 即 4096 组（~+12k 进程、~512MB、启动 ~20s、4096 个 WAL 与选举定时器），既无吞吐收益（见 2.2）又放大恢复抖动，纯属负担。

> 与 S0.1 的组合结论：每组复制写 ≈ 677 µs（3 节点）。若某节点有 N 组且 leader 均匀分布，则**该节点可并行服务的共识写 ≈ N × (1/677µs)**：N=8 → ~11.8k 共识写/s/节点，N=64 → ~94k/s/节点。因此"组数 N"同时是资源预算与吞吐并行度的旋钮——但 N 由预算（而非分区数）决定，G 由故障域决定。

## 4. 未覆盖项

- **多节点并行吞吐**：未实测 G 组分布在 3 节点上时并发生产者的真实聚合吞吐（需多生产者 + 多机）。
- **组数上限压测**：未跑到"进程/ETS 成为瓶颈"的拐点（本实验最大 128 组仍远在预算内）。
- **成员变更 / 快照截断对组数的放大效应**：S0.1 未覆盖，S0.2 也未；需在 S4 多机组网时补齐。
- **CPU 按组归因**：仅以进程/ETS/内存作资源代理，未做 per-group CPU profiling。
