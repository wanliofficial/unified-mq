# ADR-008：分区 Raft 分组模型、故障域与存储方案

- **状态**：已采纳（S0 定稿）
- **日期**：2026-10-14
- **关联**：README §5.3（故障域警告）/§6.2（共识层）；roadmap §2 S0.2/S0.3、Gate S0；S0.2 / S0.3 spike

## 背景（Context）

README 5.3 警告：Raft Group 数量过多会带来资源与运维开销，并放大故障波及面；同时需明确快照与日志段清理、失去多数派行为。并且需确定数据面存储方案（A=自研 WAL / B=复用现有存储）。

## 决策（Decision）

### 8.1 分组模型

- **默认每组 16 个分区**（partitions per Raft group）。
- **单节点组数受资源预算约束**：建议 ≤ 256 组/节点（≈ +768 进程、+512 ETS、+32MB、启动 ~1.3s，皆宽松）；超过该预算时**增大组大小**（如 32/64），而非增加组数。
- **故障域 = 组大小 G**：一次该组的 Leader 选举或局部故障会短暂暂停这 G 个分区的复制。G 越小隔离越好、开销越大；G 越大开销越小、爆炸半径越大。G=16 是折中默认。
- **允许按租户/命名空间下探到 G=1** 以满足强隔离需求（单租户热点分区不应连累其他租户的重选举），或少分区场景。
- **禁止大规模 1:1 分区:组**：1:1 既无吞吐收益（见 8.4）又放大恢复抖动。

### 8.2 资源依据（S0.2 实测）

单节点扫描 K={1,4,8,16,32,64,128} 组，每组固定开销**线性**：~3 进程、~2 ETS 表、~128 KB 内存、~5 ms 启动。128 组 = 473 进程 / 291 ETS / 61 MB。

### 8.3 存储方案：采用 A（自研分段 WAL + Group Commit）

S0.3 验证方案 A 可行：fsync **871 µs/msg**（1148 msg/s）；group commit batch=64 达 **~19944 msg/s（17× 提升）**；20k 记录恢复 **143 ms**；`kill -9` 后仅恢复已 fsync 前缀，重复/丢失窗口可控。故数据面采用**自研分段 WAL**，不做每业务操作走共识。

### 8.4 复制与批量（呼应 README 6.2）

本地数据面走**批量追加**；不将每个业务操作变为全局共识命令。单节点单写者吞吐不随组数上升（S0.2 实测 ~1070 写/s，被本地一次 fsync 锁死），真实聚合吞吐来自**分布在不同节点上的 Leader 并行**，每组复制写 ~677 µs（S0.1）。

### 8.5 失去多数派

按配置**停止或限制可靠写入**（L3 不可达时降级到 L1/L2 或拒绝），存量连接按 ADR-007 处置；旧 Owner 在 Epoch 变化后必须被 Fencing 拒绝（S4 验证）。

## 后果（Consequences）

- **+** 开销可控、故障域清晰、可与分区规模解耦。
- **+** 自研 WAL 可控可优化，与 ra 复制层职责分离（ADR-002/003）。
- **-** 分组策略需配置与运维理解；自研 WAL 需持续故障注入测试（恢复正确性、段清理）。
- **-** 组大小 G 是全局旋钮，需随分区规模调整并文档化。

## 验证（Validation）

S0.2 spike（分组开销与故障域输入）、S0.3 spike（WAL/fsync/group commit 可行性）、S0.1 spike（复制写成本、失去多数派拒绝）。S4 需补：快照/段清理、成员变更、Epoch Fencing、多机故障注入。
