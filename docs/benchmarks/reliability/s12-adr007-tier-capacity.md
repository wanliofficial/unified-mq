## 1. 测了什么

被测对象全部走**真实路径**，无 mock：3 个 `peer:start_link` 起的独立 BEAM 节点，真实
`ra` 集群（本机磁盘 WAL），真实 `broker_cluster_meta` 状态机，真实 `broker_queue` 数据面 +
`broker_storage_wal` 后端。分区 0 由节点 1 拥有、3 节点全为副本，因此一条
`replicated_commit` 写入是：本地 fsync → rpc 两个 follower（各自 fsync）→ 多数派检查
（`broker_cluster_rep:replicate/2`）。

四段测量：

| 段 | 测法 | 回答 |
|---|---|---|
| **1. 串行每档延迟** | 单调用方逐条 append，N=2000 | ADR-007「ACK 返回时机」在每档的逐条成本（p50/p99/max） |
| **2. 饱和每档吞吐** | 8 并发调用方各 append 3 s，聚合 | WAL group-commit（batch_size 32）把并发调用批进一次 fsync，**该档的容量天花板** |
| **3. ra 元数据层提交容量** | 单调用方逐条 `broker_cluster:assign`（真实 ra 提交，epoch 单调递增），N=2000 | S12 有状态服务**控制面**的提交天花板 |
| **4. 失多数派边界** | 停掉两个 follower，owner 上每档各 2000 | ADR-007「失去多数派时写入必须被拒绝」在容量边界的体现 |

档位定义（ADR-007）：L1 `os_buffer`（入 OS 缓冲即 ACK）、L2 `fsync`（本地 WAL fsync 后
ACK）、L3 `replicated_commit`（Raft 多数派提交后 ACK）。

## 2. 原始数字（两次运行，同主机 3 peer，1024 B 消息）

### 2.1 串行每档延迟（N=2000，逐条 ACK 可见延迟）

| 档位 | run1 p50 / p99 / max | run2 p50 / p99 / max |
|---|---|---|
| L1 `os_buffer` | 0 / 0 / 2 ms | 0 / 0 / 3 ms |
| L2 `fsync` | 3 / 6 / 14 ms | 3 / 6 / 9 ms |
| L3 `replicated_commit` | 8 / 14 / 22 ms | 7 / 11 / 16 ms |

三档延迟严格递增，且 L1 ≈ 0（不入 fsync，仅入 OS 缓冲即返回），与 ADR-007 的 ACK 时机
定义一致。

### 2.2 饱和吞吐天花板（3 s，8 并发，group-commit 批后聚合）

| 档位 | run1 msg/s | run2 msg/s |
|---|---|---|
| L1 `os_buffer` | **18 009** | **14 738** |
| L2 `fsync` | 1 979 | 1 880 |
| L3 `replicated_commit` | **882** | **851** |

天花板逐级下掉一个量级：L1 不 fsync 故最高，L2 受本地 fsync 速率约束，L3 在 fsync 之上
再叠加跨节点复制 + 多数派等待。两次运行间有 ~20–30% 波动（同主机、无隔离），故读作
**量级**而非精确值（§5）。

### 2.3 ra 元数据层（S12 有状态服务）控制面提交容量（N=2000，串行）

| 指标 | run1 | run2 |
|---|---|---|
| commits/s | 413 | 449 |
| p50 / p99 / max | 2 / 6 / 10 ms | 2 / 5 / 16 ms |

ra 把每条元数据写串行进单日志、按到达顺序 apply，因此这**就是**控制面天花板：并发客户端
只能排在它后面，加并发不会抬高它。一次 ra 提交 ~2 ms（p50）。

### 2.4 失多数派边界（停掉两个 follower，owner 上每档各 2000）

| 档位 | run1 | run2 | 判定 |
|---|---|---|---|
| L1 `os_buffer` | ok=2000 | ok=2000 | 不依赖该组，**照常成功** |
| L2 `fsync` | ok=2000 | ok=2000 | 本地落盘即 ACK，**照常成功** |
| L3 `replicated_commit` | **ok=0 / failed=2000** | **ok=0 / failed=2000** | 凑不齐多数派，**逐条拒绝** |

这是三档**绑定到 S12 有状态服务**的硬证据：ra 元数据组的可用性**只门控 L3**。L1/L2 的
持久化锚在本机磁盘 WAL，从不向该组求助，所以组失多数派对它们无影响；L3 的持久化锚在
多数派，组不可用时**必须**被拒绝而非静默成功（ADR-007「额外约束」，已由 S0.1 spike 首次
验证，本容量专项在真实 3 peer + 真实 ra 组上复现）。

## 3. 怎么读这些数字

- **三档容量比 ≈ 17 : 2 : 1（L1 : L2 : L3）。** 以 run2 为例：`os_buffer` 14 738 msg/s、
  `fsync` 1 880 msg/s、`replicated_commit` 851 msg/s。从 L1 到 L2 掉一个数量级是「是否 fsync」
  的分界；从 L2 到 L3 再减半是「跨节点复制 + 多数派等待」的成本。这与 ADR-007 给三档的
   **实测成本**排序（fsync ~871 µs/msg、组复制 ~677 µs/写）同源，本容量专项把它落到
  **msg/s 天花板**上。
- **控制面比数据面 L3 还慢一个量级。** ra 元数据提交 ~450 commits/s，而数据面 L3 饱和吞吐
  ~850 msg/s。即每写一条消息到 L3，约每两条才摊到一次元数据变更的份额。S12 的再平衡 /
  归属变更 / shared 认领都走这条控制面（`broker_cluster_meta`），因此**元数据操作天然是
 低频、毫秒级**的——这正是 `broker_rebalance`「一轮一移 + 冷却窗口」设计成立的前提：
  再平衡不是高吞吐路径，控制面容量不构成瓶颈（参见
  [`2026-11-19-s12c-rebalance.md`](../2026-11-19-s12c-rebalance.md)：一次完整搬迁 ~2 ms）。
- **L3 的尾部是「多数派是否凑齐」。** 串行 L3 p99 ≈ 11–14 ms、max ≈ 16–22 ms，比 L2 的
  p99 ≈ 6 ms 多出的部分就是一个跨节点 RTT + follower fsync。本机 RTT 近 0，故这个差值就是
  follower fsync 的成本；跨机时 RTT 会主导（§5）。

## 4. 断言 ↔ 设计要求

| 设计要求（ADR-007 / Gate S12） | 断言 | 证据 |
|---|---|---|
| 三档 ACK 返回时机严格递增（L1 < L2 < L3） | 串行 p50/p99 严格递增；L1 ≈ 0 | §2.1 |
| 三档容量逐级递减、可量化 | 饱和吞吐 17 : 2 : 1 | §2.2 |
| 有状态服务（ra 元数据层）的持久化容量可测 | ra 提交 ~450 commits/s、p50 ~2 ms | §2.3 |
| 失去多数派时 L3 写入被拒绝，不静默成功 | L3 ok=0 / failed=2000 | §2.4 |
| 失多数派不波及 L1/L2（它们锚本机磁盘） | L1/L2 各 ok=2000 | §2.4 |
| 崩溃节点重入并追平 epoch | （非本报告，由 CT 证明） | `broker_cluster_dist_SUITE:a_crashed_node_rejoins_and_catches_up` |

## 5. 口径限制

- **同主机、单机、3 节点。** 所有数字是**下界**。跨机 / 跨 AZ 时，L3 的跨节点复制 RTT
  会成为主导项：本机 RTT ≈ 0 使 L3 仅比 L2 慢 ~1 ms，跨 AZ（RTT ~1 ms）会让 L3 串行延迟
  上升一个量级，跨地域（RTT ~30–60 ms）会到数十 ms。**本仓无跨机集群证据**，以上是基于
  RTT 的推算，不是实测。
- **只测元数据提交，不测「追平」。** S12 不迁移活进程（ADR-032 D5），故本专项的有状态服务
  只覆盖 ra 元数据层 + WAL，不含消费者 / 队列内容的迁移追赶。
- **未测并发尾延迟。** 数据面吞吐用 8 并发聚合，但分位延迟取自串行调用方；高并发下的
  WAL pending 队列（`max_pending_appends` 4096）尾延迟未测。
- **波动 ~20–30%。** 同主机无 CPU / IO 隔离，两次运行吞吐有波动，故吞吐读作量级。
- **未测 `os_buffer` 的丢失。** 三档的丢失边界已由
  [`s2-b-osbuffer-loss.md`](s2-b-osbuffer-loss.md) 用替身 + dm-flakey 真掉电档实测；本
  容量专项只补「吞吐 / 延迟天花板 + 失多数派拒绝」，不重复掉电语义。
- **冷路径已预热。** 各段首条 append 视为 warmup，不计入模块加载 / leader 首次发现的
  一次性成本。

## 6. 结论

ADR-007 三档在容量层面是**可量化、可预期**的：同主机 3 peer 下，串行 ACK 延迟
L1 ≈ 0 < L2 ≈ 3 ms < L3 ≈ 7–8 ms，饱和吞吐天花板 ≈ 14.7k : 1.9k : 0.85k msg/s，
逐级掉一个数量级。把上限**绑定到 S12 有状态服务（ra 元数据层）**后得到两条硬结论：

1. **控制面容量（~450 ra 提交/s、单次 ~2 ms）远低于数据面 L3（~850 msg/s）**，故 S12 的
   归属 / 再平衡 / shared 认领等元数据操作是低频毫秒级动作，不构成吞吐瓶颈——这正是
   ADR-032「一轮一移 + 冷却窗口」与 ADR-021 两阶段迁移设计成立的前提。
2. **失多数派时三档优雅降级**：L3 逐条拒绝（ok=0），L1/L2 照常成功（ok=2000）。这证明
   ra 元数据组的可用性**只门控 `replicated_commit`**，与 ADR-007「失去多数派时写入必须被
   拒绝或显式降级，不得静默成功」的约束一致。

至此 Gate S12「有状态服务的状态持久化与崩溃恢复有测试证明，并绑定 ADR-007 显式可靠性
等级」一项的证据齐备：崩溃恢复（CT）、丢失边界（s2-b）、容量与失多数派边界（本报告）。
