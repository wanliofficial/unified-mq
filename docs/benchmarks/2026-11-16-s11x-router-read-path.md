## 0. 结论

三个实现现在**各差一个变量**：

| 标记 | 含义 |
|---|---|
| `old` | 平表索引；env 通过 `gen_server:call` 取（改动前） |
| `env` | 平表索引；env 直接读（**仅改动 1**） |
| `trie` | trie 索引；env 直接读（**改动 1 + 2**） |

单进程 `route/3`，p50：

| 订阅数 | old | env（改动 1） | trie（改动 1+2） |
|---|---|---|---|
| 1 | 43,268 ops/s / 21 µs | **84,094 / 13 µs** | 70,463 / 19 µs |
| 1,000 | 456 / 2,097 µs | 474 / 1,984 µs | **53,623 / 19 µs** |
| 10,000 | 42 / 23,014 µs | 42 / 22,510 µs | **51,928 / 19 µs** |

三个结论（与 v1 不同）：

1. **改动 1 只在索引很小时有意义**。1 订阅时省下约 8 µs（21 → 13 µs，1.9x），因为那时整条路径只有一次调用。**1,000 订阅以上，改动 1 几乎无用**（2,097 → 1,984 µs，仅快 5%），因为全表拷贝彻底盖过了调用成本。
2. **大表下的收益几乎全部来自改动 2**：1,000 订阅 456 → 53,623 ops/s（**118x**），10,000 订阅 42 → 51,928（**1,236x**）。
3. **trie 在小索引上有固定代价**：1 订阅时 trie（19 µs）比平表（13 µs）慢，因为按层走 map 查找的成本超过了「扫 1 行」。这个代价在 1,000 订阅时已被反超 100 倍以上，但如实记录。

**改动 1 的真正价值不在单进程吞吐，而在并发扩展性**：它移除了写者进程作为聚合吞吐的天花板。见 [`2026-11-16-s11x-router-concurrency.md`](2026-11-16-s11x-router-concurrency.md)。

## 1. 机器与口径

| 项 | 值 |
|---|---|
| CPU | AMD Ryzen 7 4800U（16 逻辑核） |
| 内存 | 15.7 GiB（压测时有其它负载，见下） |
| OTP / ERTS | 28.3.1 / 16.2 |
| 运行形态 | 裸 VM，无 release、无 Docker、无网络 |
| 被测函数 | `route/3`（「消息已到 → `[{Partition, Refs}]`」这一步） |
| 写入方式 | 经真实写者 `broker_router_hash:register/4`，每条一次 call |
| 并发 | 单进程紧循环（并发数据见单独报告） |
| 采样 | 预热 250 ms，测量 1500 ms；p50 取 201 次单次调用的中位数 |

**机器当时有其他负载**（load average 6–8 / 16 核）。同一轮内三种实现交替跑，**相对关系**有效；**绝对吞吐偏低**，引用时请在空闲机器复跑。

**这不是端到端 MQTT 吞吐**，与 [`2026-11-08-s2-baseline.md`](2026-11-08-s2-baseline.md) 的 875→1056 msg/s 不可直接相除比较。

### 1.1 三个实现怎么做到「各差一个变量」

v1 的根本缺陷是 `env` 和 `trie` 都调用 `broker_router_hash:route/3`——同一个函数，同一份实现。于是那两行的数字必然几乎相等，而 v1 把它解读成「改动 1 独立就够」。

更正后的做法：

- **平表索引**由基准自己建（`ets:new(flat_index, [set, protected, {read_concurrency, true}])`），每 filter 一行 `{{Tenant, FilterBin}, [{Ref, Seq}]}`，在 setup 阶段一次性灌好、不计时。
- **`old` 的那次 `gen_server:call`** 由独立模块 `tools/bench/flat_env.erl` 提供，用真实 `gen_server:call` 而不是裸 `send/receive`——后者缺少 monitor 与回复跳转，会**低估**被测量的成本。
- **`env`** 直接用 `maps:get(flat, Env)` 拿表引用，其余与 `old` 完全相同。
- **`trie`** 走真实 `broker_router_hash:route/3`。

所以 `old` vs `env` 只差「取 env 是否需要一次调用」，`env` vs `trie` 只差「索引是平表还是 trie」。

### 1.2 平表与 trie 的行数不同，这不影响可比性

平表每 filter 1 行；trie 的行是**路径**。本形状下 1,000 订阅 = 1,000 平表行 / 2,106 trie 行。`old`/`env` 扫的是自己的平表，`trie` 走自己的路径索引——这正是两种实现的真实差异，不是口径偏差。行数差异的来源见 [`2026-11-16-s11x-router-index-memory.md`](2026-11-16-s11x-router-index-memory.md)。

### 1.3 v1 里那些自伤 bug（保留，因为教训仍然成立）

构造这个基准时，**基准自身**出过五次错，每次都靠断言而不是靠读代码发现。前三条来自 v1，后两条在 v2 更正时才暴露：

| 症状 | 根因 | 现在的防线 |
|---|---|---|
| 三行都是 `matched => 0` | 手写的 `Dest` 没有任何 filter 覆盖 | 断言 `Matched =/= []` |
| `index_rows => 0` | 在 `teardown()` **之后**读表，ETS 已删除 | 所有数字在 teardown 前读完 |
| 每行 `refs => []` | 把 `route/3` 的返回值当成 `{Ref, Seq}` 二元组，实际是裸 SubRef | 断言改为对裸 SubRef 做 `lists:member` |
| `bench/#` 行匹配为空 | trie 的叶子行与中间行都是 `{Children, Subs}` 形状，靠形状判断会把「同时是前缀又是 filter」的行误判为中间行 | 按 `Subs` 是否为空判断是否为 filter |
| **`env` 与 `trie` 数字几乎相同** | **两者调用同一份代码** | **`env` 改用独立平表；新增 `old`/`env`/`trie` 三行匹配数与邻居对比** |

最后一条最危险：它不产生任何异常，只是让一个**不存在的结论**看起来有数据支撑。这类错误只能靠「这个数字为什么恰好等于另一个」的疑问发现。

## 3. 这份数据没证明什么

1. **没证明 trie 在 1 万订阅内比「只做改动 1」快** —— 这一点已被证明（118x / 1,236x），但**没证明 trie 在更小规模下也值得**：1 订阅时 trie 比平表慢。盈亏平衡点未精确测量，大致在「索引行数 ≫ 路径深度」之后。
2. **没测端到端吞吐**（含网络、编解码、存储）。
3. **没测内存** —— 已另行补测（[`2026-11-16-s11x-router-index-memory.md`](2026-11-16-s11x-router-index-memory.md)）。
4. **每个点只跑一轮**，没有多轮重复取中位数；1k 档与 10k 档的相对高低（53,623 vs 51,928）在噪声内，不要解读。
5. **绝对数字受机器负载影响**（§1）。
6. **没测有写入并发时的读延迟/吞吐**。每次测量索引都是冻结的。**正确性**已单独覆盖：`broker_router_hash_SUITE:route_sees_stable_subscriptions_while_the_index_churns` 在并发 churn 下跑 4.2 万次 route，断言从未注销的订阅必须每次都被匹配，0 漏匹配；并用变异测试确认该断言能失败。但「churn 期间的 route 延迟」没有数字。

## 4. 对后续决策的影响

- §7.3 要求的三档数字**已补齐**，且三个实现真正互相独立（§1.1）。
- **改动 1 的定位需要修正**：它不是「性能优化」，而是**移除并发天花板**。单进程大表下它几乎不带来收益（5%），并发小表下它把 4.16x 提升到 7.48x。见并发报告。
- **改动 2 是大表收益的全部来源**，也是唯一让曲线变平的因素。
- **改动 3（计划缓存）**的结论见扇出报告的 §4 —— v1 基于错误的 `env` 行得出「无需改动 3」，该结论同样作废并已更正。
