# S12-C 再平衡与迁移的耗时实测（2026-11-19）

> 本报告回答 Gate S12 的「容量 / 迁移耗时报告」一项：把 `broker_rebalance` 的
> 一次搬迁**实际**花掉多少时间测出来。方法、原始数字与口径限制都在下面，
> 数字是本机、同主机、3 peer 下的一次运行，**不是**跨机、跨地域的结论。

## 1. 测了什么

「一次再平衡搬迁」在本仓是两步 raft 写（ADR-021 D3 两阶段）：

```
migrate(P, From, To, E)      %% 归属改到 To，epoch=E，state=migrating
finish_migration(P, E + 1)   %% state=active，epoch=E+1
```

因此把**一次完整搬迁的墙钟时间**定义为 `migrate/4` + `finish_migration/2`
两次提交成功为止，另测决策路径与单条 raft 写作为参照。

被测对象全部走**真实路径**：3 个 `peer:start_link` 起的独立 BEAM 节点，
真实 `ra` 集群（本机磁盘 WAL），真实 `broker_cluster_meta` 状态机，
真实 `broker_cluster_cache` 本地镜像。没有 mock。

## 2. 原始数字

`n = 200` 次，同一台主机，3 个 peer，每次搬迁的分区/owner 在 0~7 号分区、
两个 owner 之间轮换（不复用同一 epoch，因此不存在「写被旧 epoch 挡掉」的
干扰；每轮都强制一次 leader 复制 + 一次本地缓存 apply）。

| 操作 | p50 | p95 | p99 | max |
|---|---|---|---|---|
| **一次完整搬迁**（`migrate` + `finish_migration`） | **2024 µs** | **3432 µs** | **4230 µs** | **4788 µs** |
| `broker_rebalance:step/1`（含决策 + 一次搬迁） | 244 µs | 358 µs | 400 µs | 5341 µs |
| `broker_rebalance:evaluate/1`（纯决策，无写） | 226 µs | 312 µs | 366 µs | 405 µs |
| `broker_cluster:assign/4`（单条 raft 写） | 1125 µs | 1527 µs | 1767 µs | 2040 µs |

## 3. 怎么读这些数字

**决策几乎免费。** `evaluate/1` 是纯内存算术（读本地 `broker_cluster_cache`
视图 + `broker_cluster_meta:members()`），p50 **226 µs**、max **405 µs**，
且与集群规模无关。`step/1` 在多数样本上就是「决策 + 0 次写」= 244 µs，
说明**均衡本身不构成延迟风险**。

**搬迁成本 ≈ 两条 raft 写 + 一次决策**，p50 **2.0 ms**。其中单条
`assign/4` 的 p50 是 **1.1 ms**，所以两条写（约 2.2 ms 的理论值）与实测
2.0 ms 一致——**cost 几乎全在共识提交，不在搬迁逻辑**。

两个具体含义：

- **cooldown 的 300000 ms（5 分钟）默认值远大于实测搬迁成本（2 ms）。**
  这是刻意的：cooldown 是防振荡的旋钮，不是性能预算。2 ms 的搬迁即便
  不做冷却也不会拖垮控制面；冷却存在是为了让「刚搬完的分区」在客户端
  重连窗口内保持稳定。
- **搬迁期间业务不受影响。** 迁移只改 `(owner, epoch)`，源在 `migrating`
  期间仍可读（`broker_rebalance_dist_SUITE` 已断言），旧 epoch 的写入被
  `{fenced,_}` 拒绝、新 owner 接受当前 epoch。**没有数据搬运、没有连接
  中断、没有队列暂停**，所以「搬迁要多久」对业务延迟的贡献是**零**——
  2 ms 是元数据提交的时间，不是消息排队的时间。

## 4. 口径限制（别外推）

- **同主机、单机、3 节点。** 这个数字是**下界**。跨机、跨 AZ 时 raft 的
  RTT 会成为主导项：一次搬迁 = 2 次多数派提交 ≈ 2×（1 个 RTT + fsync），
  跨 AZ（RTT ~1 ms）大约在 **2~4 ms** 量级，跨地域（RTT ~30~60 ms）会到
  **100 ms 以上**。**本仓没有跨机集群证据**，以上是基于 RTT 的推算，
  不是实测。要拿到真实数字需要多机部署 + 时钟同步。
- **冷路径已预热。** 首轮 200 次之前各跑了一次搬迁做 warmup，因此没有
  计入模块加载、leader 首次发现、缓存冷填充的一次性成本。生产环境首次
  搬迁可能慢一个数量级（数百 ms），属正常。
- **只测元数据提交，不测「追平」**。搬迁完成（`finish_migration`）后，
  新 owner 的缓存立即更新；但**活进程/队列内容的迁移不在 S12-C 范围**
  （ADR-032 D5，R-RB5/R-RB6 标「S12 不交付」），消费者靠重连重建
  （ADR-019）。**没有「迁移耗时」之外的业务追赶时间**可测。
- **未测并发**。所有样本串行执行。`broker_rebalance` 是单进程内的一次
  命令、无内部队列，并发搬迁会被 raft 的串行化天然排队，不会互相踩踏，
  但排队深度下的尾延迟未测。

## 5. 结论

S12-C 的再平衡在元数据层面是**毫秒级、对业务透明**的操作：决策 0.2 ms、
搬迁 2 ms（同主机 3 peer）。它不构成延迟预算上的风险，真正的边界是
**冷却窗口**与**活进程不迁移**（ADR-032 D5），不是耗时。本报告的
2 ms 是同主机下界；跨机数字需另行实测，本仓当前无跨机集群。
