# S11-C 容量测量：CoAP over DTLS（PSK）

日期：2026-11-16　OTP 28.3.1（erts 16.2）　机器：AMD Ryzen 7 4800U，16 逻辑核，16 GiB，Linux 6.18

本报告回答设计 §9 的问句：**在真实 broker 链路上，DTLS 的握手成本、请求往返成本、并发请求吞吐各是多少，代价落在哪里**。所有数字都是本机实测，不是估算。

## 1. 口径与「不是什么」

- 驱动的是**真实** `coap_listener`（`transport => dtls`）+ 真实应用链（`broker_storage`/`router`/`queue`/`retain`/`subscription`），不是桩。请求走完整 dispatch 路径。
- 客户端是**真实 PSK 客户端**（Erlang `ssl`，`{protocol,dtls}` + `user_lookup_fun` + cert-free PSK 套件），与 `coap_dtls_SUITE` 用的是同一条协议路径。选 Erlang 而非 Python：Python 3.12 的 `ssl` 无法在不带证书的情况下提供 PSK identity，测不到真实路径（详见 `2026-11-16-s11c-dtls-psk-spike.md`）。
- **不含** libcoap/C 客户端的互操作证据（S11-C 明确推迟，单列）。
- 全部绑 `port => 0` 回环，不碰 8080/8083/1883/8081/8082/8084/3478，不进 `rebar3 ct`。
- **限流不在被测范围内**：`max_requests_per_second` 默认 100/端点，超出即静默拒绝。测量时抬到 10^6（见 §5 的第 3 条——这正是本次测量第一个踩到的坑）。

## 3. 结果矩阵

### 3.1 顺序握手（`handshake`，200 次，每次 connect→warmup→close）

| 指标 | 值 |
|---|---|
| 吞吐 | **41 次/秒** |
| p50 | **22.1 ms** |
| p95 | **29.9 ms** |
| mean | 24.6 ms |
| max | 216 ms（首次，含 `ssl` 应用冷启动） |

这是 §3.2 串行 acceptor 的上界：`1 / 22ms ≈ 45`。串行化是**故意的**——PSK identity 只能在 `user_lookup_fun` 里观察到，而该回调同步跑在 `ssl:handshake/2` 内、把消息投给持有回调状态的进程；并发握手时无法判断一条 identity 消息属于哪条连接（实测：被拒绝的身份串进了下一条连接）。

### 3.2 请求往返（`rtt`，500 次，单条长连接，payload 64 B）

| 指标 | 值 |
|---|---|
| p50 | **347 µs** |
| p95 | **447 µs** |
| mean | 356 µs |
| max | 559 µs |

### 3.3 并发请求吞吐（`throughput`，每 worker 100 次 GET，会话**先顺序建好**再计时）

| 并发 | req/s | 请求数 | 错误 |
|---|---|---|---|
| 1 | **2839** | 100 | **0** |
| 8 | **4747** | 800 | **0** |
| 32 | **4440** | 3200 | **0** |

8 → 32 并发不涨反略降（4747 → 4440），说明瓶颈已经不在监听器单进程之外的调度上：所有会话的入向解密与 dispatch 都经由**同一个** listener 进程。这是「单 listener = 单核上限」的直观体现，约 **4.4k req/s** 见顶。

### 3.4 明文 UDP 对照（同一节点、同机、成对测量）

| 指标 | DTLS | 明文 UDP | 比值 |
|---|---|---|---|
| p50 | 347 µs | **189 µs** | 1.84× |
| p95 | 447 µs | 263 µs | 1.70× |

即一条已建立会话上，DTLS 的加解密 + ssl 进程间投递约让单次往返**近乎翻倍**（+158 µs）。绝对量级（亚毫秒）对 CoAP 这类小报文场景是可接受的。

### 3.5 连接风暴（`connect_storm`，32 个 peer **同时**发起握手，客户端超时 20 s）

本行 `run_bench.sh` 固定测 N=32（原始 JSON 的 `latencies_ms` 给出完整分布）：

| 并发 N | 成功 | 延迟分布（ms） |
|---|---|---|
| 32 | **5/32** | 32, 1028, 3030, 7032, 15030, 20003–20008（其余 27 个全在 20 s 超时） |

N=1/2/4/8/16 的曲线来自单独探针 `s11c_storm_probe`（同 listener、同客户端路径，一次性扫描，未纳入 `run_bench.sh`）：

| 并发 N | 成功 | 延迟分布（ms） |
|---|---|---|
| 1 | 1/1 | 26 |
| 2 | 2/2 | 26, 1025 |
| 4 | 4/4 | 23, 1025, 3026, 7031 |
| 8 | **5/8** | 26, 1024, 3029, 7026, 15029, 20004×3 |
| 16 | **5/16** | 26, 1027, 3029, 7027, 15028, 20004×11 |

对照组——**同批 peer 错开 150 ms** 发起（bench 内建 `staggered`，原始 JSON 已含，实测 32/32 全成功）：

| 指标 | 同时发起 | 错开 150 ms |
|---|---|---|
| 成功 | **5/32** | **32/32** |
| p50 | 20005 ms | **22 ms** |
| p95 | 20007 ms | **25 ms** |

结论非常明确：**串行 acceptor 本身不是瓶颈**（错开时 22–27 ms/次、全部成功），**同时发起**才是。机制是 DTLS 客户端重传退避：N 个 ClientHello 同时到达，只有队首被 `ssl:transport_accept` + `ssl:handshake` 处理，其余在 listen 队列里等待；客户端等不到 ServerHello 就按 1 s → 2 s → 4 s → 8 s 指数退避重传，于是观测到的成功时刻精确落在 1 s / 3 s / 7 s / 15 s 的刻度上（N=32 的 `latencies_ms` = `[32, 1028, 3030, 7032, 15030, 20003…20008]`，与退避步严丝合缝）。

- 这是**连接延迟**，不是请求吞吐——吞吐矩阵（§3.3）在会话建好后零错误。
- 对本阶段的含义：**设备冷启动必须错峰**（建议 ≥ 150 ms 的随机抖动，或由运维侧分批上线）。按 §3.1 的 41 次/秒，理论上限是每秒可纳管 41 台新设备；实际受客户端退避影响，同时上线超过 ~5 台就会有可感知的延迟。
- 这是设计 §3.2「串行化」的已知代价，已在设计 §11 风险表登记。真要提升，需要并发握手 + 另一种身份归属方案（OTP 目前不提供），不在本期范围。

## 4. 与能力的对应关系（写进兼容性矩阵的口径）

- **握手速率 41/s**：决定「每秒可接入的新设备数」，不是稳态承载。
- **单会话 RTT 347 µs p50 / 447 µs p95**：决定单设备的交互时延上限。
- **稳态约 4.4k req/s（单 listener、单节点、零错误）**：决定单节点承载的请求量；再多需要多 listener 分片（不同端口/地址），本期未做。
- 上述数字**不含** OSCORE（未做）、Block2 服务端分块（未做）的开销。

## 5. 测量过程中发现并修正的三个口径错误（重要）

这三个都曾让数字看起来「有问题」，但全部是**测量口径**问题，不是产品缺陷；记录在此以免后人重踩。

1. **把建连成本算进了请求吞吐。** 早期版本让每个 worker 自己 `connect` 后立刻打请求，于是 N=8 时只连上 3–4 个（其余落入 §3.5 的重传退避），吞吐被读成 12 req/s。改成「先顺序建好全部会话，再并发计时」后，同一台机器上是 4700+ req/s。**建连与请求是两件事，必须分开测。**
2. **测量撞上了限流器。** `max_requests_per_second` 默认 100/端点，超出的请求被静默拒绝。症状极具误导性：失败**恰好从第 100 个请求开始**、随后每 4 个失败 1 个，看着像「每 N 个包丢一个」的传输层缺陷。抬到 10^6 后零错误。**任何吞吐测量都必须先确认没有限流在起作用。**（`dtls_bench` 已在启动时把该项抬到 `max_request_rate/0`，并在注释里说明原因。）
3. **DTLS 客户端在拆连时会让 bench 崩掉。** `ssl:close/1` 在已半死的 DTLS 客户端上可能从 `dtls_client_connection:init` 抛 `{bad_action_from_state_function, ...}`；因为风暴 worker 用的是 `spawn_link`，一个客户端拆连失败就把整个 bench 带走。已改为 `spawn_monitor` + `catch ssl:close/1`，失败只计入统计。

## 6. 结论

- DTLS 的代价是**可量化且温和**的：单次往返 +158 µs（约 1.8×），握手 22 ms/次。
- 稳态请求吞吐在本机约 **4.4k req/s**，瓶颈是单 listener 进程而非 DTLS 本身；扩展路径是多 listener 分片。
- 唯一需要运维关注的行为是**冷启动风暴**：同时上线设备必须错峰，否则客户端重传退避会把接入延迟拉到秒级。这是串行握手的必然结果，已如实声明为能力边界，而非缺陷。
